# Report Charts Readability — Design

**Date:** 2026-05-30
**Status:** Approved (pending spec review)

## Problem

The profile/range report is generated by a single LLM call (`server/src/prompts.ts` →
`profileReport.ts`) that is asked to write prose *and* hand-draw inline SVG charts in one
shot. With no layout engine or text measurement, the LLM produces unreadable charts:

- X-axis date labels printed on top of each other (`2026-05-24` piled up).
- Categorical bar labels run together (`weekday (40h)weekend (20h)`).
- Donut/pie labels stamped *inside* the circle (`focus time (20h)` centered on the ring).
- Invented, meaningless chart types (concentric circles for "Focus Time").

Asking the same prompt to "make labels readable" is unreliable — the next generation drifts
again because there is no deterministic layout and the chart instructions compete with the
prose instructions for the model's attention.

## Approach

Keep the LLM as the chart generator (charts stay HTML/CSS/SVG), but **split report generation
into two focused LLM calls** and **pre-compute all chart numbers on the server** so the chart
LLM only does layout, never arithmetic:

1. **Report call** — produces the written report only (no charts): title, optional response to
   the user's custom request, per-goal analysis cards, and the 10 recommendations.
2. **Chart call** — receives the written report text *plus* a server-computed, ready-to-plot
   dataset, and produces only the 5 chart blocks as a scoped HTML/SVG fragment.

The server then **combines both fragments into one document** and returns the existing
`{ title, html }` shape. No iOS changes required — `ProfileReportGenerator` and
`ReportDetailView` are untouched.

All system prompts continue to live centrally in `server/src/prompts.ts`.

### Why two prompts + server-side math

- The chart prompt can be ruthlessly strict about layout without diluting the prose prompt.
- Feeding the chart call the finished report lets captions reference the same framing/numbers
  the prose used, so the document reads as one coherent piece.
- Pre-aggregating every dataset on the server (totals, %, day-of-week averages, daily stacks,
  weekly rollups, goal targets) removes the most common failure mode after layout: the LLM
  miscomputing values. The LLM receives final numbers and only places them.

## Data flow

```
iOS (unchanged)
  └─ POST /profile-report { rangeStart, rangeEnd, tz, goals, customPrompt, days }
       │
server: profileReportHandler
  ├─ validate (unchanged Zod schema)
  ├─ buildReportUserPrompt(...)            ── existing aggregation
  ├─ LLM call #1 (REPORT) ─────────────►   { title, reportHtml }
  ├─ buildChartDatasets(days, goals)       ── NEW: pre-computed, ready-to-plot numbers
  ├─ buildChartUserPrompt(reportText, datasets)
  ├─ LLM call #2 (CHARTS) ─────────────►   { chartsHtml }
  ├─ combineDocument(reportHtml, chartsHtml)
  └─ res.json({ title, html })             ── same contract as today
```

### Combining the two fragments

The report fragment emits a single placeholder marker where charts belong — after the goal
analysis and before the recommendations (data first, then advice):

```html
<!-- CW_CHARTS -->
```

`combineDocument` splices the charts fragment into that marker. If the marker is absent
(model omitted it), charts are appended after the report as a fallback. Both fragments scope
their `<style>` under `.cw-report`; multiple `<style>` blocks coexist fine, and the iOS wrapper
(`ReportDetailView.wrap`) is unchanged.

## The 5 charts

Each chart is chosen so its layout makes label collisions structurally impossible, and each
lives in a card with a short caption above it.

1. **Category Totals — horizontal bar chart.** One row per category: color swatch + name +
   hours on the left, bar extends right, value at the bar end. Labels are in their own left
   column and can never overlap regardless of category count. Replaces the broken vertical bars
   and the meaningless concentric circles.

2. **Category Share — donut with external legend.** A ring showing each category's share of
   total time. No text on or inside the ring. Legend is a vertical list beside/below it:
   swatch · name · hours · %.

3. **Daily Breakdown — stacked bar per day.** One vertical bar per day, segments colored by
   category. X-axis labels are thinned to a fixed maximum and rotated 45°; ranges longer than
   31 days roll up to weekly bars (server-computed). Replaces the piled-up date axis.

4. **Average by Day-of-Week — 7 bars (Mon–Sun).** Average minutes per weekday, revealing
   rhythm. Fixed 3-letter labels (`Mon`…`Sun`) under each bar — short, evenly spaced.

5. **Goal Progress — horizontal actual-vs-target bars.** For each goal with a parseable numeric
   target, a horizontal bar of hours achieved vs target, with a target marker and "X of Y h"
   label. Goals with no parseable target are omitted from this chart (edge case below).

## Chart datasets (server pre-computes)

`buildChartDatasets` produces, from the validated `days`/`goals`:

- `categoryTotals`: `[{ name, minutes, hoursLabel, pct }]`, sorted desc. Categories beyond the
  top 8 collapse into an `other` bucket so charts never overflow.
- `daily`: `[{ date, segments: [{ name, minutes }] }]` for ranges ≤ 31 days; otherwise
  `weekly`: `[{ weekStart, weekEnd, segments }]` (rollup), with a flag indicating which is used.
- `byWeekday`: `[{ weekday: "Mon"…"Sun", avgMinutes }]` averaged across occurrences in range.
- `goalProgress`: for each goal, attempt to extract a numeric weekly/total hour target from the
  free text (e.g. "80 hours per week"); when found, pair with the relevant category's actual.
- A shared `palette` map (the category→hex table already in the prompt).

## Chart prompt — strict layout rules

`CHART_GENERATION_SYSTEM_PROMPT` (new export in `prompts.ts`) enforces:

- Output is an HTML fragment containing **only** the 5 chart cards (a `<style>` block scoped
  under `.cw-report` + the chart markup). No prose, no recommendations, no `<script>`.
- Every chart uses an SVG `viewBox` with ≥ 32px margins; all axis labels, legends, and captions
  live **outside** the plot area.
- Minimum font sizes: captions 12px (uppercase muted eyebrow), all labels/values ≥ 11px.
- Categorical labels are placed horizontally in rows (bar charts) or in an external legend
  (donut) — never crammed onto a horizontal axis.
- Time-axis labels (daily breakdown) are limited to a max count, rotated 45°, and the server's
  weekly rollup is used when provided.
- Long category names truncate to a fixed character budget with an ellipsis.
- Use only the numbers supplied in the dataset; never invent or recompute values.
- One consistent palette (provided in the dataset); fixed hours formatting (`Xh`, `XhYY`, `Ym`).
- Charts render correctly at narrow widths (single column, `max-width: 100%`, `height: auto`).

## Report prompt changes

`PROFILE_REPORT_SYSTEM_PROMPT` is revised to:

- Produce **only** prose: header (title + date range), optional custom-request response, goal
  cards, and exactly 10 recommendations. **No charts, no SVG.**
- Emit the `<!-- CW_CHARTS -->` marker between the goal cards and the recommendations.
- Keep the same visual style rules (background, card chrome, headings, scoping under
  `.cw-report`) and still return `{ title, html }`.

## Orchestration changes (`profileReport.ts`)

- Two sequential `together.chat.completions.create` calls. If call #2 (charts) fails, return the
  report fragment without charts rather than failing the whole request (degrade gracefully).
- `max_tokens` tuned per call (report ~3000, charts ~5000) instead of one 8000 budget.
- `responseSchema` for the report call: `{ title, html }`. Chart call returns `{ html }`.
- New helpers: `buildChartDatasets`, `buildChartUserPrompt`, `combineDocument`.

## Edge cases

- **No data tracked:** report renders normally; charts section shows a short "not enough data"
  note instead of empty SVGs.
- **Single day in range:** daily breakdown is one bar; day-of-week shows only the populated day.
- **Goal with no numeric target:** omitted from Goal Progress; if no goal has a target, the
  Goal Progress chart is skipped entirely (4 charts render).
- **Many categories (>8):** collapsed into `other` by `buildChartDatasets`.
- **Chart call returns invalid/empty HTML:** fall back to report-only document.

## Out of scope

- iOS / SwiftUI changes (contract unchanged).
- Native Swift Charts rendering.
- Changing the PDF export path.
- Caching or persisting the two-call intermediate outputs.

## Testing

- Unit tests for `buildChartDatasets`: totals/%, top-8 collapse, weekday averaging, weekly
  rollup threshold, goal-target parsing.
- Unit test for `combineDocument`: marker splice + append fallback.
- Manual: generate reports for a 7-day, 31-day, and 92-day range and confirm no overlapping
  labels in any of the 5 charts (the original failure modes from the screenshots).
