# Daily Reminder Insights (Push Notifications) — Design

**Status:** 📥 Backlog — design only, not scheduled for implementation
**Scope:** iOS Swift app (`ios-swift/`) + capture-proxy server (`server/`) + new scheduled job + Firebase Cloud Messaging
**Date:** 2026-05-31

## Summary

Every day at 9:00 PM (the user's local time, by default) Cronwatch sends a push
notification reminding the user to fill in their time tracking. The notification
body is **dynamically generated by an LLM** (Together AI, a cheap model) and is
short, motivational, and insightful — grounded in the user's goals and their
**week-to-date** tracking progress. Each generated message is an "insight": a
one-to-two-sentence statement. Messages are stored in Firestore so the user can
scroll through a history of past insights inside the app. In Profile settings the
user can turn the reminder off or change the time of day it is sent.

This is a "real push" design: a server-side scheduled job generates the message,
stores it, and delivers it via Firebase Cloud Messaging (APNs) so it appears on
the lock screen even when the app is closed.

## Goals (of this feature)

- A daily, on-time nudge that actually reaches the user even if the app is closed.
- Messages feel personal: they reference the user's real goals and this week's
  actual tracked time, not generic platitudes.
- A persistent, scrollable history of past insights ("Insights" feed) in the app.
- User control: a single toggle to disable, and a time picker to reschedule.
- Reuse the existing Together AI integration and the central prompt file
  (`server/src/prompts.ts`); keep all numbers deterministic and only let the LLM
  write prose.
- Cheap: one short LLM call per active user per day on a small model.

## Non-goals

- Android / web parity (iOS-only first pass).
- Multiple reminders per day, or per-category reminders.
- Two-way notifications (actionable buttons, reply-to-log). A tap just opens the app.
- In-notification streak gamification beyond what the message text conveys.
- Editing or deleting individual past insights.
- Localization / non-English messages (English only first pass).

## User experience (iOS)

### Profile → Notifications settings (new section)

```
Reminders
  [x] Daily check-in reminder            (toggle)
      Remind me at   [ 9:00 PM ]         (time picker, only shown when on)
      "A short, motivational nudge based on your goals and this week's progress."
```

- First time the user enables the toggle, the app requests push-notification
  permission (`UNUserNotificationCenter.requestAuthorization`). If denied, show an
  inline note linking to iOS Settings and keep the stored preference "on" so it
  resumes if they grant permission later.
- Changing the time writes immediately to Firestore (debounced); the server job
  reads it on the next tick.

### Insights feed (new, scrollable history)

- A simple reverse-chronological list of past insight cards (date + message text).
- Reachable from Profile ("View past insights") and/or as the destination when the
  user taps the push notification.
- Backed by a Firestore snapshot listener on the `insights` subcollection
  (paged/limited to e.g. the most recent 60).

## Data model

### Firestore: `users/{uid}` (extend existing doc)

Add a `reminders` map alongside the existing `goals`/vision fields:

```
users/{uid}
  reminders: {
    enabled: bool            // default true on first onboarding completion
    hour: int                // 0–23, local hour to send (default 21 = 9 PM)
    minute: int              // 0–59 (default 0)
    timeZone: string         // IANA tz id, e.g. "America/Los_Angeles"
    lastSentLocalDate: string// "YYYY-MM-DD" in user's tz — idempotency guard
  }
  fcmTokens: {               // map of token -> metadata (a user may have >1 device)
    "<token>": { platform: "ios", updatedAt: Timestamp }
  }
```

`timeZone` is captured/updated by the app on launch so the server can compute the
user's local 9 PM. `lastSentLocalDate` prevents double-sends if the job overlaps a
tick boundary.

### Firestore: `users/{uid}/insights/{insightId}` (new subcollection)

```
users/{uid}/insights/{insightId}
  text: string             // the generated insight (1–2 sentences)
  createdAt: Timestamp      // server timestamp
  localDate: string         // "YYYY-MM-DD" for grouping/dedupe
  model: string             // which Together model produced it (for tuning)
  delivered: bool           // true once FCM accepted it
  context: {                // snapshot of what fed the prompt (debug/tuning)
    weekMinutesByCategory: { [category]: int }
    goals: [{ category, weeklyTargetHours }]
  }
}
```

### Firestore rules (`firestore.rules`)

- `users/{uid}/insights/{insightId}`: `allow read: if owner`. Writes are
  server-only (Admin SDK bypasses rules), so **no client write rule** is added —
  keep insights tamper-proof.
- `fcmTokens` lives inside the existing `users/{uid}` doc, already covered by the
  self-only `read, write` rule. (Acceptable; alternatively split into a subcollection
  if we want to restrict client writes to token registration only.)

## Server architecture

### 1. Push infrastructure (Firebase Cloud Messaging + APNs)

One-time setup (documented as a checklist, not code):

1. Create an **APNs Authentication Key** (.p8) in the Apple Developer portal and
   upload it to the Firebase Console (Project Settings → Cloud Messaging). FCM then
   delivers to iOS via APNs.
2. iOS: add the **Push Notifications** capability and **Background Modes → Remote
   notifications** in `project.yml` / entitlements; add `FirebaseMessaging` via SPM.
3. iOS: register for remote notifications, implement
   `MessagingDelegate.messaging(_:didReceiveRegistrationToken:)`, and write the FCM
   token to `users/{uid}.fcmTokens` (and clear it on sign-out / token refresh).
4. Server: use `firebase-admin`'s `getMessaging().send()` (already have the Admin
   SDK initialized in `server/src/firebase.ts` — no new dependency).

### 2. Insight generation module (`server/src/dailyInsight.ts`, new)

A single function `generateInsight(ctx) → { text, model }` that:

- Aggregates the user's **week-to-date** tracked minutes per category (Monday→now
  in the user's tz) from `users/{uid}/entries`, reusing the same aggregation shape
  the report pipeline already builds (`chartData.ts`'s `aggregateTotals`).
- Builds a compact user prompt: goals (category + weekly target hours), week-to-date
  minutes per category, optionally the "wantsToBeBetterAt" / vision text, and the
  current day-of-week so the model knows how much of the week remains.
- Calls Together AI with the new system prompt (below) on a **cheap model**,
  `temperature ≈ 0.8`, `max_tokens ≈ 120`, `response_format` JSON
  `{ "insight": "<text>" }`.
- Returns the validated single sentence(s). All numbers in the prompt are
  pre-computed server-side; the model only writes prose (same discipline as the
  report pipeline).

Model: add `TOGETHER_INSIGHT_MODEL` to `env.ts`, default to a cheap small model
such as `meta-llama/Meta-Llama-3.1-8B-Instruct-Turbo`. Keep it configurable so we
can A/B different cheap models.

### 3. The system prompt (lives in `server/src/prompts.ts`)

Add and export a new constant so it can be tweaked alongside the others. Draft:

```ts
// ─── Daily reminder insight ──────────────────────────────────────────────────

export const DAILY_INSIGHT_SYSTEM_PROMPT = `You write a single short push-notification message that nudges a user to fill in their daily time tracking in a time-tracking app called Cronwatch.

You will receive:
- The user's goals (each with a category and a weekly target in hours). Some may be absent.
- The user's time already tracked THIS WEEK so far, per category (in minutes), pre-computed.
- What day of the week it is now (so you know how much of the week remains).
- Optionally, a free-text note about what the user wants to get better at, or their longer-term vision.

Write ONE message that is:
- Motivational and genuinely insightful — connect their current week's progress to a goal or to their bigger vision.
- Specific: reference a real number or a real goal when it makes the message land harder (e.g. "You're 4h into your 10h deep-work goal — log tonight to keep the momentum").
- Short: 1–2 sentences, under ~200 characters, readable at a glance on a lock screen.
- Action-oriented: it must end by reminding them to log / fill in today's time tracking.
- Warm and human, never preachy, never guilt-trippy. Vary the angle day to day.

Hard rules:
- Use ONLY the numbers you are given. Never invent hours, streaks, or categories.
- If little or nothing is tracked this week, encourage a fresh start rather than shaming.
- No emojis unless they add real warmth (at most one). No hashtags. No markdown.

Respond with STRICT JSON: {"insight": "<the message>"}. No prose around it, no code fences.`;
```

### 4. Scheduled job (the trigger)

DigitalOcean App Platform supports **scheduled Jobs** (cron). Add a second component
to `server/.do/app.yaml` of `kind: job` with `schedule` (e.g. every 15 minutes:
`*/15 * * * *`) running a new entrypoint `node dist/jobs/sendReminders.js`. (Sharing
the same Docker image; the job overrides the run command.)

The job, on each tick:

1. Query `users` where `reminders.enabled == true`.
2. For each user, compute their current local time from `reminders.timeZone`. If the
   local time is within the tick window of their `reminders.hour:minute`, **and**
   `reminders.lastSentLocalDate` ≠ today's local date, they are due.
3. For each due user with ≥1 `fcmTokens`: `generateInsight()`, write the
   `insights` doc, send the FCM push (notification title "Cronwatch" + body = insight,
   with a `data` payload routing to the Insights feed), then set
   `lastSentLocalDate`. Prune any FCM tokens FCM reports as unregistered.

Idempotency is provided by `lastSentLocalDate`; a missed tick (deploy/restart) just
sends late on the next tick, never twice.

> **Alternative considered:** a Firebase Cloud Function on a Pub/Sub schedule. Rejected
> for now to keep all server logic in the one existing Express/Node deployment and avoid
> introducing the Functions toolchain. Revisit if we move off DO App Platform.

## Data flow

```
[DO scheduled job, every 15m]
        │  query users where reminders.enabled
        ▼
   due now & not yet sent today?
        │ yes
        ▼
  aggregate week-to-date entries  ──►  generateInsight()  ──►  Together AI (cheap model)
        │                                                          │ {"insight": "..."}
        ▼                                                          ▼
  write users/{uid}/insights/{id}  ◄────────────────────────── validated text
        │
        ▼
  FCM send (notification + route data)  ──►  APNs  ──►  device lock screen
        │
        ▼
  set reminders.lastSentLocalDate = today (local)

[iOS app]
  Profile toggle/time  ──► writes users/{uid}.reminders
  launch               ──► writes fcmTokens + reminders.timeZone
  tap notification     ──► opens Insights feed (snapshot listener on insights)
```

## Error handling & edge cases

- **No goals / nothing tracked this week:** prompt instructs an encouraging
  fresh-start tone; still send.
- **LLM failure:** fall back to a small set of hand-written static reminder strings
  so the user still gets a nudge; mark the insight doc `model: "fallback"`.
- **No FCM token (never granted permission / signed out):** skip the push but still
  generate+store the insight so the feed stays populated when they return. (Decide
  during planning whether to skip generation entirely to save cost — see open questions.)
- **Timezone missing/invalid:** default to the value last seen, else `UTC`; skip
  rather than guess wildly.
- **Token rejected by FCM (`messaging/registration-token-not-registered`):** remove
  it from `fcmTokens`.
- **Permission denied in iOS:** keep stored preference, surface a "notifications are
  off in iOS Settings" hint.
- **DST / clock changes:** computing local time from the IANA tz each tick handles
  this automatically.

## Cost

One short call (~300 input tokens, ~60 output) per active user per day on an 8B-class
Together model is fractions of a cent per user per month. The 15-minute cron does N
cheap Firestore queries; negligible.

## Testing

- **Server unit tests** (`node:test`, matching existing `*.test.ts`):
  - "due now" logic across timezones, DST boundaries, and the `lastSentLocalDate` guard.
  - week-to-date aggregation (reuse/extend `chartData.test.ts` patterns).
  - `generateInsight` JSON parsing + fallback path (mock Together).
- **iOS:** unit-test the `reminders` settings model encode/decode (extend
  `UserSettingsTests.swift`); manual device test for permission + token + delivery.
- **Manual:** a one-off admin script / route to force-send to a single uid for QA.

## Phased implementation (when pulled off backlog)

1. **Prompt + generation (no delivery).** Add `DAILY_INSIGHT_SYSTEM_PROMPT` to
   `prompts.ts`, `TOGETHER_INSIGHT_MODEL` to `env.ts`, and `dailyInsight.ts` with a
   manual test route. Verify message quality before wiring anything else.
2. **Storage + Insights feed (iOS).** `insights` subcollection + rules; iOS feed view
   reading it. Lets us dogfood message quality via the feed before push is set up.
3. **Settings (iOS).** `reminders` map + Profile toggle/time picker.
4. **Push plumbing.** APNs key, FCM SDK on iOS, token registration to `fcmTokens`.
5. **Scheduled job.** `jobs/sendReminders.ts` + `app.yaml` job component + idempotency.

Stopping after step 1 or 2 already delivers value (an insights feed) with near-zero infra risk.

## Open questions (resolve at planning time)

- Generate-and-store even when the user has no push token (keeps the feed warm) vs.
  skip to save cost? (Leaning: generate if reminders enabled, regardless of token.)
- Notification title/branding and whether to include a tiny streak count in the body.
- Cron granularity: 15 min (tighter delivery, more job runs) vs. hourly (cheaper,
  ±up-to-59-min delivery). 15 min recommended.
- Should disabling the toggle also stop generation (no feed entries) or just stop the
  push? (Leaning: stop both.)
